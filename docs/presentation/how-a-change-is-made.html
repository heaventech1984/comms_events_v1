How a change is written down

  • For anyone looking after this app.
  • You do not need to have made software before.
  • A private calendar for one Birmingham community.

Read the project read-me next to this film.

First

Words go on a board before anyone changes the program.

  • A wish is one piece of paper.
  • A broken thing today is a repair.
  • An agreed rule is a different board again.

Put the words in the right note. Then stop, unless someone asked you to build.

Which board

Four places new words can go.

  • An idea for later goes on the wish list.
  • Something broken today is a repair.
  • A change already being checked gets a comment.
  • A rule the team has agreed goes in the decisions note.

The read-me names the file for each one.

When it ships

Write what went out. Then move the wish.

  • The dated ship notes say what the demo gained.
  • Then the wish moves to the built list, with a link back.
  • The wish list is not a pile of work you start alone.

Leaders can also type a note on the Feedback page. An admin copies the row that counts.

Making the change

Small steps, on the working line.

  • Bring in other people’s latest pages first.
  • Stay on the line called experiment.
  • Change as little as you can. Run the two checks.
  • Save and share only when a person asks.

Picture guides cover the first day, saving, and reading someone else’s change.

Ask first

Some files need a yes before you touch them.

  • The private settings file, and real people’s details, stay off the shared shelf.
  • The shape of the database, and the version number, wait for a person.
  • The live walk is the Oracle address. Leave the Railway spare as it is.

The full ask-first list is in the read-me.

You can stop

Open one note. Do that one thing.

  • You do not have to learn the whole program today.
  • The read-me is the map. Each step has a link.
  • The film is the same path, spoken once.
